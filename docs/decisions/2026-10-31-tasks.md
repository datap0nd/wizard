# 2026-10-31 — Tasks run from Settings and save to the knowledge base

**Owner:** project owner. **Status:** decided (31 October 2026).

**Context.** Work for Gemini on the work PC was a kit of 22 numbered Gemini CLI task files (`workpc/tasks/`), run by
hand in the install folder, copied there by each update, writing working files the person then published with
`.\docs.ps1 kb-publish`. The owner: "Scrap all the previous tasks ... from now on, everything is like pending tasks
where you write it for Gemini to execute ... we push them and they stay as tasks ... it would be really cool if we
didn't need to update the app for the tasks to appear there ... The output of the task is the GitHub repo." And:
"make every section collapsed by default."

**Options.** (1) Keep the Gemini CLI kit and launch it from Settings: still files and a shell, still an update per new
task. (2) Wizard runs each task as its own Gemini run with the tools it already has, and the output is committed to the
knowledge base the way portal maps are. (3) Give task runs a file-and-command workspace on the PC: closest to the old
kit, but a free write surface beside Wizard's read-only rule.

**Decision.** Option 2.
- **Where tasks live.** One Markdown file per task in the Wizard repository's `tasks/` folder (front matter: id, title,
  summary, added; then the instructions). Wizard reads the folder from `api.github.com` at runtime, the route the update
  check uses on the work network: one conditional request per check, files downloaded only when they change, checked
  again at most every 5 minutes unless the person asks. With no answer it keeps the last list it read, and before any
  answer it shows the copy bundled with the installed version. A task removed from the folder leaves the list.
- **Running one.** Settings → Tasks lists them with their last run on this PC (to do, running with **Watch it**, done,
  failed, stopped) and **Run**. A run is a Gemini run of kind `task` in a conversation of its own, one task at a time
  per person, beside a question and a mapping. Its prompt is the task's instructions inside a fixed frame: work on your
  own, read the standard, change only what is asked, never invent, end with what changed.
- **What it produces** goes to the company's knowledge-base repository through three tools: `wizard_kb_note_source`
  (a note's file as it is), `wizard_kb_standard` (the knowledge standard) and `wizard_kb_save_notes` (whole notes under
  `knowledge/`, one commit per save with this PC's write token). Every note is checked with the content validator
  first, its id must be its file name and may not belong to another note, and nothing is committed when one fails.
  `wizard_kb_save_notes` is refused outside a task run, so answering a question never changes the knowledge base.
- **Who.** Only the person at a single-person install (the same rule as publishing the Pages site): the write token is
  theirs.
- **Retired.** `workpc/tasks/` and the `/wizard:tasks` command. Setup removes the installed copies. The documentation
  kit (`.\docs.ps1`) stays.
- **Settings sections** start collapsed.

**Consequences.**
- A new task needs no update; a task that needs a tool Wizard does not have still does.
- The tasks folder is public: tasks hold instructions only, never company content (tasks/README.md).
- The first task: add mapped portal reports to the metric notes' "Where to get it" (section 11 of the standard).

**Evidence.** `tests/unit/test_tasks.py`: tasks from GitHub with a conditional request, the bundled copy and the last
good list as fallbacks; the task prompt; reading and saving notes, with every refusal saving nothing; no write token;
a task run from Settings saves a note while a question is refused; tasks only for the PC's owner; setup removes the old
files. `apps/web/src/components/TasksPanel.test.tsx`; Settings sections checked collapsed in the browser.
