# 2026-10-30 — Brain and Cases on the company GitHub's Pages; Gemini names each chat

**Owner:** project owner. **Status:** decided (30 October 2026).

**Context.** The owner: "use the same repo (wizard-content in my github enterprise), where my knowledge base lives, to
build /brain using that in github pages and make it available for other people to see", and "build /cases where, when I
make a prompt, and get a response, I can put the cases there so people can see the successful analysis. ... on the left,
we have the prompt, an arrow to the right, a window with the result, then if there's more interactions, an arrow to the
bottom with the follow up prompt, then arrow to the left etc etc. Different color for the prompts and for the answers."
After seeing a mockup: "I like the title idea. Right now, there's no title generated by gemini for each chat too", "I
like it, build it please", "Dont make them related. Brain and Cases are two different links, and you need to know the
URL for both", and "wizard will do this in the work PC, leveraging the regular credentials already loaded in". While
this was built: "I'm mapping ASAP and I mapped like 120 reports. I see that /brain didnt change much though. Still says
3 reports catalogued."

**Decision.**
- **Two pages of their own.** The site has `brain/` and `cases/`, each at its own address; neither links to the other
  and there is no home page between them. Each page's top shows the Wizard mark and its own name only.
- **Published from the work PC, at the person's click, with the write token already there.** Wizard writes the site
  with the knowledge base's write token (Settings → Knowledge base), as one commit through the company GitHub's API, to
  a branch of the knowledge-base repository that is not the notes' own: `gh-pages`, an orphan branch that shares no
  history with the notes. Every PC downloads the notes' branch whenever it changes; none downloads this one. Settings →
  Pages site can name another repository (`WIZARD_SITE_REPO`, which the write token must then cover), another branch
  (`WIZARD_SITE_BRANCH`, never the notes' branch) and the site's address (`WIZARD_SITE_URL`). Only the person at a
  single-person install publishes (`local-owner`, install or desktop mode), never a shared server. Every write is audited
  (`site:brain_publish`, `site:case_publish`, `site:case_remove`) and refused for a public repository, like every write
  Wizard makes.
- **Pages is turned on once by hand.** A Contents-only token may neither turn Pages on nor read its address: a repository
  admin chooses Settings → Pages → Deploy from a branch → `gh-pages` → / (root), and the person copies the address GitHub
  shows into Settings → Pages site. Until then Wizard says so instead of guessing an address. Who can open the pages is
  the company GitHub's own Pages setting, not Wizard's.
- **Brain** is the in-app `/brain` page drawn from a snapshot: **Publish** on the Brain page writes `brain/brain.json`,
  the map and the news as this person's Wizard reads them at that moment (note titles, summaries, tags, links, the
  systems, the reports mapped in each portal, the news counts and latest headlines; never a note's text). On the site
  the page has no sign-in, no refresh and no way into the app, and the news is labelled SNAPSHOT with the time it was
  read, never LIVE.
- **Cases.** **Share as case** in a chat's header (shown when publishing is possible and the chat has a finished answer)
  opens a panel: the title (Gemini's name for the chat to start with), an optional takeaway, the answers to share (all
  at first), a **Preview** in Wizard (`/case/<chat>`, the page as it would be published) and **Publish**, later
  **Update the case** and **Remove from the site**. It says before the click what everyone who can open the site will see:
  the prompts and answers, their charts and tables, data labels and the names of their sources, never the sources' rows
  (each source keeps only its id, system, report name, data mode, as-of date and row count), and that figures read with
  the person's own rights are shown as they saw them. A chat keeps one case address however often it is published;
  `cases/cases.json` lists the cases, newest first. A case that looks like it holds a credential is refused.
- **The case page draws the owner's snake.** Prompt 1 on the left in Samsung Blue, an arrow right to Wizard's answer in
  a white window (its data label and check status in the title bar, its charts and tables as in the app, its sources and
  "What Wizard did" below); an arrow down on the side the answer ended to the follow-up prompt, an arrow left to its
  answer, down again, and so on. On a narrow screen every step stacks with arrows down. The gallery lists the cases with
  a search and a filter by system.
- **Gemini names each chat.** With the Code Assist runtime (the desktop's), the first question of a chat is also sent to
  Gemini as one small request on the quicker of the person's two models, under their own sign-in: "Name this analysis
  for a list of chats", at most 8 words. It runs beside the answer, which waits at most 5 seconds for it before it shows
  as finished. The name replaces the question only while the chat still carries it: a name the person gave it stays, and
  a follow-up never renames it. Without a name from Gemini (another runtime, a refusal) the chat keeps its question.
- **The reports mapped in a portal show in /brain.** The Brain page now reads each portal's map on this PC (or the one
  published to the knowledge base): the Sources panel says "120 reports mapped" for a mapped portal, and each report
  Gemini mapped (or partly mapped) is a point joined to its portal, on its own layer, **Portal reports mapped**. Reports
  only found, not yet mapped, are counted, not drawn.

**What this does not do.** Wizard never turns Pages on, changes who may open it, or publishes on its own. Gemini has no
tool for any of this: the site is the person's click. The pages read only their own JSON files; nothing on them calls
Wizard.

**Evidence.** `tests/unit/test_site.py` (8: an orphan branch and the notes' branch untouched; read, remove and skip
unchanged files; the page's own HTML; a credential refused; Share as case end to end over a replayed analysis: preview,
publish with title and takeaway, the case's sources without rows, publish again to one address, remove; Brain as a
snapshot without note text and the address left to Settings; only the person at this PC, and only with a write token;
the branch is never the notes' own), `tests/unit/test_titles.py` (8: the name cleaned to one line; asked of the quicker
model under the person's project, without tools; none when Gemini cannot say; a name the person gave stays; the first
answer names the chat, a follow-up does not), `tests/unit/test_brain.py` (mapped and partly mapped reports counted and
drawn, found-only ones counted; the API reads the map on this PC), `apps/web/src/cases.test.ts`, `CaseFlow.test.tsx`
and `graph3d.test.ts` (the snake's sides and drops, the gallery's search, the chosen answers; portal reports drawn around
their portal on their own layer). The built site was served from a Pages-like sub-path and checked in Chromium at
1280×800, 1440×900 and 390×844 (a three-prompt synthetic case, the gallery and the Brain snapshot), with no console
errors and no sideways scroll. Not run: the company GitHub's Pages itself, which first serves the branch when the owner
turns Pages on.

**Addendum, 9 November 2026.** The owner: "cases has all the queries and steps instead of an expandable option for
it. Also, I want that 'download' or copy button to be in Cases." Under each answer, one closed section ("How Wizard got
this answer (N sources, M steps)") holds the sources, each still opening its query, and the steps; a citation in the
answer still opens its query directly. Each visual of a case has the same Copy / download menu as in Wizard; its Excel
file holds the visual's own values and the sources (names, data labels, queries), never their rows.
[Decision](2026-11-09-heatmaps-and-visual-exports.md).

**Addendum, 6 November 2026.** The owner: "Brain should have a link to cases page." The Brain page's header links to
Cases: on the site to `../cases/` beside it, in the app to the site's Cases page when Wizard knows the site's address
(Settings → Pages site, or found once on the publisher's PC; `site.cases` in the bootstrap, never asked of GitHub for
it). Cases still does not link to Brain, and the site has no home page. Evidence: `tests/unit/test_site.py`,
`BrainPage.test.tsx` and the e2e test "the Brain page opens once on the pixel wizard diving into his brain, and links to
Cases"; [the Brain decision](2026-10-28-brain-page.md) has the rest of that day's change.

**Addendum, 4 November 2026.** The owner: "In Cases pages, we're seeing that the queries it's doing are clickable but they
dont open the query itself ... Its just strictly visual." Each source of a case now also keeps the query that read it
(`site.query_of`): the SQL as written (and its database); a portal read's steps, each with what it did, its address
without the host, its body and script, secrets removed; else the request Wizard sent. A file the person attached keeps
none: its name and folder stay on their PC. Never a source's rows. A click on an evidence chip in the answer, a source
chip or a step's evidence opens it in a window with Copy. Share as case says so before the click. A case published
before keeps no queries until it is published again.
